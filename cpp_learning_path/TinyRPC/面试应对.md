## 一、原理类

### Q1. 协程和线程切换为什么差两个数量级？
线程切换要陷内核走 syscall、经过调度器 + futex 唤醒、保存完整上下文（含 FPU/SSE）并切内核栈，~1μs；协程纯用户态，只存 **12 个 callee-saved 通用寄存器 + RSP + RIP 共 14 个 slot**（`coctx_swap.S`），~10ns。没存 rax/r10/r11 是因为 SysV ABI 把它们定义为 caller-saved。

### Q2. 时间轮怎么运作？按系统时间吗？
**不按系统时间查询**，而是每过一个 tick_ms（由 sleep 或 timerfd 驱动）`current_index` 前进一格，对应 bucket 整桶 pop，本质是"相对滴答数"而非绝对时间戳。精度就是 tick_ms，所以换来了 O(1) 插入/删除。

### Q3. 你 TinyRPC 的定时系统？
**两层结构**：底层是 `timerfd + std::multimap` 的**精确定时器**（O(logN)，给 RPC 超时/sleep_hook 用）；上面叠一个**单层时间轮 `TcpTimeWheel`** 专做连接空闲检测——连接有活动就 `fresh(slot)` 塞到队尾 bucket，每 10s 轮子转一格丢最老 bucket，slot 析构触发连接关闭。

### Q4. epoll 为什么比 select 快？什么场景反而不划算？
三点：fd 集合常驻内核红黑树不用每次拷贝、就绪检测靠回调 O(活跃数) 而非 O(N) 遍历、返回直接给就绪数组。**连接少且高度活跃、或短连接频繁建销时反而不划算**，因为 `epoll_ctl` 的红黑树增删开销比 select 一次性遍历更贵；io_uring 是下一代，连 read/write 都零 syscall。

## 二、项目深挖

### Q5. 你项目最大短板是什么？
**两个**：① Main Reactor 单线程 accept，10w QPS 以上成瓶颈，改进方向 `SO_REUSEPORT` 多 listen fd 分摊；② 慢 handler 会拖垮整个 IO 线程的其他连接（HOL blocking），改进方向拆独立 worker 线程池 + eventfd 回写，彻底版是 brpc bthread 那种 M:N。这么设计是为了 IO 线程 fast path 无锁，是个 tradeoff。

### Q6. 协程池大小怎么选？怎么检测泄漏？
池大小 **1000**，按 QPS × 协程持有时长估算 + 压测拐点验证，超池容量就 fallback 到堆上 new。泄漏检测三件套：运行时 `active_count` 曲线（Prometheus）、协程创建时记 backtrace 定期扫存活超阈值的、ASan/Valgrind 压测抓栈对象未析构路径。

### Q7. 单个请求处理 100ms 会怎样？怎么解决？
会**阻塞整个 IO 线程上其他所有连接**（HOL blocking），因为协作式协程不会被抢占，P99 会爆。四层方案：handler 内主动 `Yield`、拆 worker 线程池分离 IO 与业务、快慢队列隔离、业务层超时 + 熔断。

### Q8. TinyPB 序列化 10MB 大对象会怎样？
**三重问题**：内存放大 2-3 倍（Protobuf string + 发送 buffer 双拷贝）、`write` 反复 EAGAIN 占住 IO 线程几十 ms、接收端 buffer 频繁 realloc 卡顿。优化方向：`writev`/`MSG_ZEROCOPY` 零拷贝、流式分 chunk、压缩、max_packet_size 保护（目前没有，已知短板）。

### Q8.5. BusTub 32 线程百万 KV 怎么测的？
**官方 leaderboard 是 20000 keys 测锁竞争**（Ratio = 无锁时间/串行时间），不是百万；我**本地另加了一个 32 线程 100 万 KV 并发 benchmark** 作为补充，shuffle 后每线程分 31250 key，先并发 Insert 再并发 Lookup。实测 **Insert 3.4w ops/s，Lookup 3.1w ops/s，100 万全部命中**，BufferPool 4096 页 16MB 内存盘；瓶颈主要是 **BPM 的 page_table 全局锁**（InnoDB 用分 instance 优化），不是 B+Tree 本身。

### Q9. 14w QPS 怎么测的？
`wrk -c 1000 -t 8 -d 30` 压 HTTP echo 接口，CentOS 虚拟机 4 核 6G，IO 线程 4 时达到峰值 14w QPS、平均延迟 9.8ms——这是**按原作者方法本地复现的**数据。echo 反映的是框架 IO 调度上限，真实 Protobuf RPC 大概 6-8w。

### Q10. 为什么不跑在本地机器？
wrk 是 CPU 密集型工具，和服务端同机会**争抢 CPU**，测到的是两者共同瓶颈而非服务端真实吞吐；同机走 loopback 也会跳过网卡和真实网络栈，结果偏乐观。

## 三、Linux 排查实战

### Q11. 两台机器 TCP 连接很慢，怎么排查？
四层排查：`ping/mtr` 看链路丢包 → `ss -tinp` 看 cwnd/retrans/RTT + `tcpdump` 看重传零窗口 → `sysctl` 查拥塞控制和 buffer 上限 → `strace -T` 看应用 syscall 耗时。高频病因是 MTU 黑洞、BDP 没打满 sendbuf 太小、Nagle + 延迟 ACK 组合。

### Q12. CPU 100% 怎么定位？
三步：`top -H -p <pid>` 定位热点线程 TID → `perf top` 或 `perf record -g` + 火焰图定位热点函数 → 结合 debug symbol 定位代码行。分类判断：用户态 100% 多是死循环、sys 占比高用 `strace -c` 看 syscall、大量 futex 是锁竞争。

### Q13. socket write 卡住可能是什么原因？
**阻塞 socket**：内核 sendbuf 满（对端没 read / 网络拥塞）、对端通告 rwnd=0 零窗口探测、丢包导致 cwnd 打回 1。**非阻塞 socket** 只会返回 EAGAIN 不会卡，真正"卡"是没监听 EPOLLOUT 导致 buffer 一直满；三连排查：`ss -tn` 看 Send-Q、`tcpdump` 看零窗口、`strace -e write` 看返回值。

### Q14. tcpdump 怎么用？
常用 `sudo tcpdump -i any -nn host x and port y -w x.pcap` 抓包存文件，Wireshark 打开分析；线上多用 flag 过滤定位建连问题，比如 `tcp[tcpflags] & tcp-rst != 0` 抓 RST、`tcp-syn` 抓握手。要点：一定加过滤 + `-c N` 限量 + `-s 0` 抓完整包，别打爆硬盘。

## 四、反问 / 开放题（一面踩坑的领域）

### Q15. 二面会问哪些？还有八股吗？
八股比例降到 ~30%，且会**从"知不知道"变成"能不能用"**——比如一面问 TCP 握手，二面问 CLOSE_WAIT 怎么排查。重点四块：项目深挖极端场景 40%、系统设计 25%（长连接推送 / 服务发现）、Linux 排查 20%（字节网络岗必考）、C++/OS 底层 15%。

### Q16. 反问："你项目最大问题是什么？"
别说"啥都差"也别吹"差不多"。**承认具体短板 + 理由 + 改进方向**：单 Main Reactor 瓶颈 → REUSEPORT；慢 handler 拖垮 IO 线程 → worker 池分离。
