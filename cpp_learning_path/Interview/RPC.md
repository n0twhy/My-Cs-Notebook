## 你提到协程切换大约 50ns，对比 pthread 1-2µs 快了很多。请从 CPU 寄存器和内核调度的角度，详细讲讲这节省下来的时间具体花在了哪里？
协程切换本质是用户态函数级上下文切换，只改少量寄存器和栈指针，不进内核、不走调度器，所以常见几十纳秒。pthread 切换要进入内核，经过调度器选线程、runqueue 锁、上下文切换再返回用户态，还伴随更明显的缓存扰动，所以是微秒级。省下来的时间主要就是内核调度路径和特权级切换这部分。

## 怎么线程间传递信息的
我这个 RPC 的线程间传递不是直接传业务 protobuf 对象，而是主线程只负责 accept，把连接和协程任务投递给 IO 线程；请求数据在 IO 线程内通过 buffer 解码成业务对象，分发执行业务后再编码回写。这样线程间传的是“任务和连接所有权”，不是“业务数据实体”，锁更少、并发更稳。

## TLS (Thread Local Storage) 陷阱： 在 M:N 模型中，一个协程前一秒可能在 Thread A 上运行，挂起恢复后可能被调度到了 Thread B 上。如果在业务代码里使用了 C++ 的 thread_local 变量，会发生什么灾难性的后果？针对这种情况，你的框架有提供类似 Coroutine Local Storage 的机制吗？

 M:N 下，thread_local 是按线程隔离，不是按协程隔离。协程一旦跨线程恢复，thread_local 上下文不会跟着走，会出现 trace_id、用户态上下文、甚至连接句柄串线。我的框架里关键链路用的是协程内置 RunTime，在 Resume 时绑定当前协程上下文，避免把请求元数据放在线程 TLS 上。它相当于简化版 CLS，但目前还不是通用的 Coroutine Local Storage 容器。

 ## 未被 Hook 的阻塞调用： 你 Hook 了 read/write/connect。但假设上层业务开发同学在你的协程里，调用了一个第三方的同步 DNS 解析库（比如原生的 gethostbyname），或者直接调用了 sleep(1)，你的调度器会发生什么？（核心考点： 整个底层物理线程会被阻塞，导致该线程上的其他协程全部饿死。你会怎么防范或监控这种行为？）

 在我这个协程调度器里，未被 hook 的阻塞调用会阻塞整个物理线程，这个线程上的其他协程都会被拖住。补充一点，我项目里 sleep 已经 hook 掉了，不会卡线程；真正风险是 DNS 解析、第三方同步库这类未 hook 调用。我的治理是三层：规范禁止、阻塞调用下沉线程池、关键系统调用逐步补 hook；再配合 loop lag 和协程执行时长监控，及时发现并定位阻塞点。

 ## “你的协程栈是怎么分配的？是使用 malloc 在堆上分配的一块固定大小的内存吗？假设你分配了 128KB 的栈，如果业务侧在一个协程里递归调用过深，或者声明了一个超大的局部变量导致栈溢出 (Stack Overflow)，你的框架会发生什么？有没有提供类似 mprotect 的机制设置 Guard Page（保护页）来捕获这种段错误，防止整个进程崩溃？”
我这版协程栈是固定大小块，从协程内存池里切分出来，当前实现底层是 malloc 的连续内存。这个设计快，但如果业务递归过深或局部变量过大，会发生栈越界。由于我还没加 mprotect guard page，越界可能先破坏邻接内存，再以随机方式崩溃，最坏是整个进程 SIGSEGV。现在只有 coredump 兜底定位，下一步会改成 mmap + 页对齐 + guard page 来做硬保护。

## “简历中提到用 timerfd 做定时器管理。如果我有 100 万个并发连接，每个连接都有一个超时定时器。你是为每个连接创建一个 timerfd 吗？（大忌，会导致 fd 耗尽）。如果只用一个 timerfd 统一管理，底层是用什么数据结构维护这 100 万个超时时间的？增删改的时间复杂度分别是多少？”
我不会每连接建 timerfd，而是每个 Reactor 只有一个 timerfd 统一驱动。通用定时任务用 multimap 管到期时间，增删是 logN 级别；但 100 万连接超时管理走时间轮，连接刷新是 O(1)，每个 tick 也是 O(1)+过期桶处理成本，所以能避免 fd 爆炸和高频 logN 开销。

## 你的 M:N 模型中，如果有 4 个物理线程（M=4），当一个新的 RPC 请求进来（accept），是 4 个线程的 epoll 去竞争这一个连接，还是有一个单独的 Acceptor 线程统一接收后，再分发给另外 3 个 Worker 线程？如果是分发，底层是怎么通知到对应线程的？（考点：eventfd 或 pipe 的跨线程唤醒）。

我这版不是多线程竞争 accept，而是 MainReactor 单点 accept，新连接进来后按 RR 分发到某个 IO 线程。跨线程通知靠每个 Reactor 自带的 eventfd：投递任务后往目标 Reactor 的 wakefd 写数据，目标线程 epoll 立刻被唤醒并消费 pending 任务。这种方式比 pipe 更轻量，语义也更清晰。
