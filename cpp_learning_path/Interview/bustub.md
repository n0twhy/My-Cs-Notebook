# 可扩展哈希表
可扩展哈希表的重点在于，我们不希望这个哈希表在扩容的时候不需要全量拷贝过去然后扩容之后又要重新进行hash运算，而是更平滑。我们都知道现在哈希表的普遍实现一般是一个指针数组然后每个指针会指向一个桶，所以这个可扩展哈希表的实现就是在你扩容的时候直接只影响其中一个桶，其他的桶还在原地完全不受影响。
我来画个图，跑一遍整体的设计
既然我们需要扩容的时候只影响其中一个桶，其他桶原地不动，这就需要我们的扩容数组的时候，可能有几个指针指向同一个桶。出现了这种情况就需要我们有粗和细的粒度，数组的粒度更细而桶的粒度更粗，这里的力度就是数组维护一个变量叫做global depth，每个桶自身也有一个变量叫做local depth这个变量的作用就在于你针对key变成的那个二进制数做几位的匹配，比如说我的global depth等于一的话我们就只取最低一位来进行二进制匹配

现在我g=1，然后分别的两个桶local depth也是一
这个key进入数组以后它先做数组那里的global depth匹配它只取最低一位，然后进入其中一个桶
```
0  ->  0000  0010
1  ->  0001  0011
```

这是我们需要插入一个key结果这两个桶都是满的这时候代表什么我们需要扩容比如说现在我们这个插入来插进来这个key是0111，现在第一指向这个桶满了，而且这个local depth和global depth是相等的，说明当前的粒度已经不够细，需要我们更进行更细致的粒度的匹配，二进制如果我们需要更细致的力度匹配我们现在是取第一位我们让它更细致一点取二位Global depth加一现在变成二所以我们整个数组变成这个样子
```
00  ->  0000  0010  (A)
01  ->  0001        (B)
10  ->  (A)
11  ->  0011  0111  (C)
```
要发生扩容的是B这个桶，他自身也需要一个更细致的力度所以他自身的local depth也加一这是我们需要取二位进行一个匹配，你能看到这里边0011和0001已经匹配不上了然后插进来这个key第二位正好也是一一我们建一个新桶C就装这两个key，把原B桶那个0011给他弄出来
嗯您能看到我们这边的一零其实他装的指针不知道该指向哪儿对吧他没有桶但是你能看到a这边的local depth是一所以他只取最低位匹配而且他这里的a桶低2位里面有00和10，所以数组这个10是完全可以指向桶A的，我们就会发现我们扩容的时候只新增了一个桶其他桶都在原地，这就是他扩容的原理

# b+树的并发难点
这个现象发生在B+树的并发测试这里
多线程混合的insert delete，现象是偶发性的，因为它是差不多跑十次然后死锁一两次，单线程测试基本没有问题。所以我知道这种低概率性的只在并发出现的基本都是多线程竞争死锁
1. 线程卡不住不动了这时候我们先不急着上GDP先打开那个Htop 看测试线程的CPU，如果CPU打满就是活锁或者死循环但如果CPU占用非常非常低线程全部sleep那就是死锁大家全都在等锁没人动。看到CPU占用接近0，嗯这一步我们就可以基本判定是死锁。

2. 方向已经确定了，是死锁。这时候我们就可以上GDP。我们先info thread先把所有的线程状态打印出来，然后再呃。Thread apply all BT。然后看一下每个线程的最后调用的栈。我们这时候就可以。其实理论上可以看到两个互相等待的线程这就是两个触发死锁的地方。为什么这个地方让我印象深刻就是因为我只看到了一个卡住的线程，这是自锁！

我仔细看了看他的线程栈，然后还有他们当时的成员变量状态我就看到一个已经持有父节点我们这里假设它等于1，去子节点pageid=2，但是拿到手以后我手上的这个page居然他的ID就是1，按照原来的逻辑我们拿到父节点的锁然后去申请孩子节点的锁这里我们拿到孩子就是自己的父节点然后我们拿着腹肌点的锁去申请父节点的锁，自锁了蹦。

3. 现在我们就要排查原因了为什么一个父节点，去取ID等于2的孩子，结果拿到了自己？
第一：我先判断是不是b+树的逻辑错误，发现不对，如果这种逻辑存在错误，单线程绝对会出问题，所以一定是并发竞争的问题
第二：我怀疑是不是自己的锁加漏了，或者顺序错了读到了脏页，我把代码逻辑通查了一遍，没问题。
第三：然后这里卡了我很久很久，最终我想到我们去下层的buffer pool去查找原因，我们取到页始终还是去buffer pool拿了这个page。如果在buffer pool那里这个页就已经存在了一些混乱的问题那么我们B+树出现错乱也是很正常的事。

4. 下沉到buffer pool我去查fetch page的流程，根因找到了，我在fetch page的时候没有把这个frame设置为不可淘汰的状态。所以完整分析下来会发现这个错乱的流程可能是这样的。父节点fetch了孩子的那个页。
但是因为没有设置不可淘汰。在另一个线程进来的时候又要flash页，然后buffer pool那边满了，我们需要淘汰一页，我们淘汰的这一页正好就是。那个孩子。然后那个线程要fetch的page正好又是这个父节点。那个线程不参与死锁，只是fetch这个父节点，存在缓冲池。回到原线程，此时他刚刚好知道自己要去哪个frame取页，这时候，他就拿到了自己的页
OK，案发现场还原了。我们。修复一下这个bug继续运行，然后跑大概几十次，终于没有出现类似的问题。

5. 这个 bug 根因其实很简单——fetch 之后漏了一行,没把 frame 设成不可淘汰,是个疏忽。
但它对我真正的意义在于:这个 bug 现象全在 B+树层,如果我只把 buffer pool 当成一个'拿页就行'的黑盒,默认它给我的 page 一定是对的,那我会一直在 B+树的加锁逻辑里打转,这辈子也定位不到——因为那一层根本没错。我能解出来,靠的是没有停在'调用它'这一步,而是去看了它的实现:fetch 到底怎么分配 frame、frame 凭什么会被复用。 这件事印证了我一个习惯——用一个组件之前,我倾向于把它的实现也看一遍,不把它当不可质疑的黑盒。 这个 bug 就是这个习惯给我的回报:修复只有一行,但能走到那一行,是因为我愿意往下沉一层去看。
# 一条SQL的输入
```
SELECT s.major, min(s.GPA) AS min_gpa
FROM student AS s
JOIN enrollment AS e
ON s.id = e.id
WHERE e.grade > 85
GROUP BY s.major
ORDER BY min_gpa DESC
LIMIT 5
```
我想要统计一个课程高分段中，每个专业的gpa水平，这个可以统计一个学生不是专业课拉胯但是公开课突击高分，他能筛选一个专业整体学风是否扎实。

## planner
```

limit 5
    |
   sort(order by)
          |
          aggr(groupby，min运算)

```
每一层都是一个执行算子，他们自底向上，每次执行一次算子都往上吐一行tuple，然后上层算子执行自己的逻辑

- 我们可以看到sort和limit两行相邻，这时候我们可以用TopK算法，这里是降序取最大的5个，就可以用最小堆来实现，具体的实现要问面试官需不需要具体讲

- 然后Fliter这里，我们可以看到他仅仅在筛选e的grade字段  不作用另一个s表，这里我们可以做一个谓词下推，把这个fliter下推到seqscan(e)这里  让他在遍历表的时候，顺便做一个比较运算来筛。访问器会看到这个e的id索引b+树存在，会把他从seq替代成indexscan

# 现代MySQL和我2022fall bustub的区别

## lockmanager
现代MySQL会在锁请求失败进入等待时，会基于当前的等待关系尝试做死锁检测，而不是像bustub那样靠后台周期性线程重建全图，形成死锁的话，会根据undolog量大小来作为参考标准abort事务。如果dfs递归过深，为了防止栈溢出，等待timeout这个超时机制兜底。
## MVCC
MVCC 的核心是“读不阻塞写，写保留旧版本”。在 InnoDB 里，每行记录有隐藏字段，比如 DB_TRX_ID 记录最后修改它的事务 id，DB_ROLL_PTR 指向 undo log 里的旧版本，所以多个 undo 记录串起来就是一条版本链。普通 select 做快照读时，会拿当前版本的事务 id 和 ReadView 判断可见性；如果当前版本不可见，就沿着 undo 链往前找旧版本。

ReadView 里核心有四个东西：创建者事务 id、当前活跃事务集合 m_ids、活跃事务最小 id min_trx_id、以及下一个将分配的事务 id max_trx_id。判断时，自己改的自己可见；小于 min_trx_id 说明早已提交，可见；大于等于 max_trx_id 说明是快照之后才来的，不可见；落在中间就看在不在活跃集合里，在就不可见，不在就可见。

RC 和 RR 的主要区别是 ReadView 创建时机：RC 每条 select 都新建 ReadView，所以可能不可重复读；RR 是事务内第一次快照读创建 ReadView，后续复用，所以普通快照读能做到可重复读。

和 Bustub 比，Bustub 更偏教学实现，用事务时间戳和 undo/version 信息把可见性机制跑通；InnoDB 更工业，undo 版本链还要配合 purge、当前读、行锁和 next-key lock。

## 缓冲池
innoDB：
```
[ young 区 / 热区，约 5/8 ]  ←→  midpoint  ←→  [ old 区 / 冷区，约 3/8 ]
   ↑ 头部(最热)                                      尾部(最先淘汰) ↑
```
young（new sublist）：热点页，约占 5/8
old（old sublist）：新进来的、可能只用一次的页，约占 3/8
midpoint：两区交界，新页插这里（不是插链表头！这就是 midpoint insertion）

新页进入，不进young，进old
第一次访问会记录一个时间戳，后续再访问时，判断是否差了1000ms，如果是，提拔进young；不是，继续呆着

### bustub缓冲池的数据结构
bufferpool里
我们都知道，bufferpool里比如这里有几个槽位，每个槽位就是一个page，这几个槽实际上就是一个Page的数组
这里我要重点讲一下，frameid这个概念，他实际上对应了两个东西，一个是数据结构Frame，这个待会儿介绍LRUK的时候讲，一个是bufferpool这里的page数组，frameid就是下标，所以拿到一个frame_id，实际上我们就能知道对应的Frame和page
在bufferpool眼里，这个frame的id实际上就是这个数组的下标，frameid对应一个page元素，page里除了真实数据以外，还维护了pin数。pin数这里我对齐一下，比如线程A要读这个页，从bufferpool取到这个页的时候pin+1，不读了还回来的时候-1，为什么，首先pin数大于0就代表有线程在读，不可淘汰！整个bufferpool还维护了一个free_list链表，记录当前空闲的frame，如果不空闲，要求lruk对象淘汰一个frame
回到frame，这个frameid在bufferpool眼里只是一个下标，但是在lruk这里，他对应了一个Frame数据结构，他里面存了这个frame历史取用的记录，和是否可被淘汰。此外lrukreplacer还维护了三个数据结构，冷(list)，热(set，根据倒数第k次访问的时间来排序)
