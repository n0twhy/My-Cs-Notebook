"M 个协程分布在 N 个 IO 线程上——每个 TcpConnection 对应 1 个协程（M 随连接数增长），所有协程调度跑在 N 个 IO 线程的 Reactor 里（N 是固定线程数）。但严格讲是 per-thread N:1 调度：协程一旦分配到某个 IO 线程就不跨线程迁移，没有 Go runtime 那种 work-stealing。所以整体呈现 M:N，单线程内是 N:1。"

# 为什么K = 2的时候性能最好
"LRU-K 的核心是区分冷热数据：只被访问 1 次的页大概率是 scan 过路的，不应该留在池子里。K=1 就退化成普通 LRU，无法区分；K=2 用'第二次访问'做冷热分水岭，成本最低、效果最好。K≥3 的话需要记录更多历史时间戳、计算开销大，而且真正热的数据很快就会访问到第 3 次以上，K=2 已经把 80% 的冷热区分做到了。论文里实验结论也是 K=2 最经济。"

# docker是什么
Docker是一种开源的容器化平台，可以将应用及其依赖打包到一个轻量级、可移植的容器里，从而实现跨环境的一致运行。容器类似于一个沙箱，彼此隔离，但共用主机的操作系统内核。相比于虚拟机，Docker容器启动更快，占用资源更少，部署和扩展更方便。常见用法包括开发、测试、部署微服务应用等。



# 虚拟内存
虚拟内存的本质是，每个进程都以为自己独占一整块连续的地址空间，实际上由CPU的MMU模块来做虚拟内存地址到物理地址的映射

## `内核区`
- PCB：进程控制块，里边就存的有进程名还有进程状态，打开了什么文件，CPU占用情况
- 页表：里边存的是虚拟地址到真实地址的映射
- 驱动：我们的用户态程序是不能直接操作硬件的，我们需要系统调用，用内核态里的这个部分区操作硬件
## `栈`
- 默认8MB，可能爆栈，比如递归过深，或者局部的数组开太大
- 当一个程序刚刚被创建时，系统里只有一个线程，这个线程就是作为目前的主线程，我们知道每个线程都有自己的私有栈，然后这里的虚拟内存的这个栈空间就是为这个主线程的私有栈准备的，随后我们可能会多开几个子线程，子线程也有自己的私有栈，就有区别于这里，他们是在mmap区
- 里面存的就有函数调用的栈帧：局部变量，返回地址
- 函数调用时压栈帧，返回时就弹出，即取即用
因为这个弹出和压栈的操作，实际上就是rsp的加减法，他是一个连续的内存，你要取得某个变量的值，实际上就是局部变量所在函数的rbp加上偏移，也是加减法

```
int add(int a, int b) {
    int sum = a + b;
    return sum;
}

int main() {
    int x = 3;
    int y = 5;
    int r = add(x, y);
    return 0;
}
```
执行 main，先在栈上放局部变量 x=3、y=5。
走到 add(x,y)，CPU 执行 call 指令：自动把返回地址（main 里下一条指令的地址）压栈，然后跳到 add 的代码地址。
走到 add(x,y)，call 指令自动压返回地址（main 下一条指令地址），跳到 add。
进 add，add 的函数序言先 push rbp 保存 main 的 rbp、mov rbp,rsp 建新基址——这步是 add 自己干的，不是 call。
add 栈帧里是参数 a、b（x、y 的副本）和局部变量 sum；x、y 是 main 的，不在这。
返回时只对 rsp 做加减，那几行字节不擦、原样留着，下次调用覆盖——就像 vector::clear()，size 归零但内存和数据没动，靠后续写入覆盖，区别是栈这里连析构都没有，更廉价。
返回值 8 走 eax 寄存器回 main。

## `空洞`(栈和mmap之间)
栈向下长，会占用这个空洞空间
## mmap区
mmap()系统调用映射出来的区域，三类东西住这
- 动态库：libc，链接的第三方库，运行时被映射进来
- 文件映射
- 大块匿名内存：malloc申请大内存，不走堆的brk()，走mmap()，free以后内存释放

### 动态库 vs 静态库
- 静态库：链接时，把整个库代码拷贝进我的可执行文件
- 动态库：链接时不拷贝，只是在可执行文件里记一笔，比如说我需要某某文件的某函数，运行时才把.so加载进内存，把地址填上

so被加载到进程空间的哪个地址，运行时才会知道，编译期根本不会把里边的函数和变量做一个链接。
#### 重定位
动态库用延迟绑定省启动开销。第一次调 printf 前，GOT 那项指向动态链接器的解析例程（不是空）。
第一次调用：代码跳 PLT 桩 → 查 GOT → 发现未解析 → 触发解析器。
解析器遍历各个 .so 的动态符号表（每个表有哈希加速，单库内快；慢在可能跨多个库依次找）找到 printf 真实地址。
把真实地址回填进 GOT。
第二次起：跳 PLT → 查 GOT → 已是真实地址，直接跳，几乎零成本。
所以首次启动有解析开销，之后运行期极快——PLT管跳转、GOT存地址

## 堆

- 向上增长
- brk()是小块调用，在堆上分配内存

### 堆为什么比栈慢

- 多线程下，堆实际上是共享的，要加锁，
- 堆的内存地址离散，cache相对不太友好

# 执行一个cpp程序发生了什么
```
#include<iostream>
int main() {
  printf("hello world");
}
```
经典四个环节
- 预处理
头文件展开，宏替换，#include <cstio>把printf的声明搬进来(注意，只是声明)
头文件里有什么：只是声明了函数，比如声明了int printf(const char *format)，但是具体的实现我们根本不知道，这个是在.so里
- 编译
语法分析，语义检查，生成汇编，编译器看到printf调用，发现他是一个外部符号，就先挖一个坑，生成一条：call printf指令，但printf的真实地址此时是未知的，先占位

注意，编译期有一个自己的符号表，检查语义的时候用
```
x      : int, global variable, defined
main   : function, returns int, defined
printf : function, returns int, declared, external
```
- 汇编
把汇编程序变成机器码
1. 生成符号表：这个.o定义了哪些符号(main),引用了哪些外部符号(printf)
2. 重定位表：记录"第几个字节这个地址要回填，等链接器来补"。
- 链接
链接器干两件事：符号决议（每个用到的符号，找到唯一提供者）+ 重定位（把代码里的占位地址回填成真实地址）。静态链接两件事链接期一次做完；动态链接，决议链接期做、地址回填甩给运行期的 ld.so。
```
printf 三阶段三凭据：
编译期靠头文件声明——能做类型检查、生成 call，地址留坑，不验真假、不碰库；
链接期靠 libc.so 的 .dynsym——确认这库导出了 printf（有实现的承诺），不报错、记依赖，碰了 .so 但只读符号表目录、不搬机器码；
运行期靠 ld.so 映射 libc.so——真实地址回填，调用成功。
```

# c++多态，虚函数的工作原理
多态的核心就在于，指针类型为基类指向其派生类，调用同名函数时，他会自动调用派生类的函数实现，而不是基类
这里我们就引申出一个概念，虚函数
在创建类时，会自动构造一个vptr，他指向位于rodata区的虚函数表，里面会记录函数定义的具体地址
运行期，他会使用对象的vptr指针指向该对象对应的虚函数表，然后跳转到派生类的函数，实现动态绑定
# 重载的工作原理
核心定义（静态多态）条件：同一作用域（或同一个类）中，函数名相同，但参数的个数、类型或顺序必须不同。 
❌️不能仅靠“返回值类型”不同来重载！因为调用时若不接收返回值（如直接写 foo(5);），编译器将无法进行重载决议。
底层机制：名字改编 (Name Mangling)
编译前端：编译器使用原函数名进行重载决议，匹配最佳的参数签名。
编译后端：编译器会将同名函数根据其参数类型，改编为独一无二的符号（例如：void foo(int) _Z3fooi，void foo(double)  _Z3food）。
链接期：符号表中每个函数名都是唯一的，链接器（Linker）根据这些唯一的函数名，精准把调用处和对应的函数体代码段链在一起。
