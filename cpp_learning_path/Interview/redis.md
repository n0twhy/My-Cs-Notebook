# Redis是什么？
是一种基于内存的数据库，读写操作全都在内存里完成

支持五种数据类型string, list, hash, set, Zset

redis支持数据的持久化，可以将数据保存在磁盘中，重启的时候可以再次加载使用(RDB,AOF)

高可用，集群(主从，哨兵)

穿透，击穿，雪崩

# Redis单线程吗
单线程redis指的是接受客户端请求，解析请求，进行数据读写操作，发送数据给客户端，这个过程是由一个线程来完成的

redis在启动的时候，会启动后台线程，3个

- 一个负责关闭文件
- 一个AOF刷盘
- 一个用来异步释放内存

# 为什么这么快？
- 单线程，无锁
- 基于内存
- IO多路复用
- 高效数据结构

## redis 6.0引入多线程
采用IO线程来处理网络请求，随着网络硬件的性能提升，redis瓶颈出现在网络IO处理上
但是对于命令的执行，仍然是单线程模型

## Redis持久化
- RDB(Redis Database SnapShot)快照，将某一瞬间的内存数据，以二进制的形式写入磁盘
- AOF日志，每执行一条写操作命令，把该命令写到一个文件里
- 混合持久化

崩溃后  AOF和RDB都能用作数据恢复
- 只用RDB，数据回退到上次BGSAVE的时候
- 只用AOF，回退到上次AOF

### AOF
先执行写操作，再写命令：避免检查开销，万一命令格式错了呢？
- Always:每次写操作执行完后，同步将日志写回磁盘
- Everysec，每次写操作完后，命令写入到AOF文件的内核buffer，每隔一秒将内核buffer写回磁盘
- No，不由Redis决定，由操作系统决定

```
写命令
  ↓
追加到 AOF buffer
  ↓
写入 AOF 文件 / OS page cache
  ↓
根据 appendfsync 策略刷盘
```
#### 重写机制
读取最新的键值对，用一条命令记录到新的AOF，历史的记录没必要了，因为已经被改了

fork子进程，利用OS的COW机制，子进程获得了一份暂时只读的快照，几乎不占物理内存，重写完成后调用rename覆盖旧文件

重写AOF时，新的写操作会暂存一个缓冲区，重写完成后再一起追加进新的AOF文件，保证数据完整

### RDB
`save`主线程生成RDB
`besave`创建一个子进程来生成RDB文件，避免主线程阻塞
Redis的RDB是全量快照，核心技术依然是COW

### 混合
子进程不再像以前那样生成set文本命令，而是把内存里的数据，全部变成二进制格式，然后这期间redis也会有写数据的操作，和AOF Buffer配合，以AOF形式保存

混合持久化影响的是AOF rewrite生成的新的AOF文件格式 → 先RDB全量快照 → AOF写


# Redis集群
主从复制是Redis高可用服务的保证
服务器可以进行读写操作，写操作自动同步至从服务器，服务器一般只读

无法实现强一致性

## 哨兵
监控主从服务器，提供主从节点故障转移功能
## 切片集群
当redis的换从数据量大到一个服务器放不下时，需要使用redis切片集群，将数据分配到不同的服务器上

根据key按照CRC算法计算一个16bit的值，再用2^14来模，均匀分配到每个服务器里面
# 有脑裂问题
加上两个参数，主节点必须要有x个从节点连接，小于这个数就不能写数据
主从数据复制和同步的延迟不能超过x秒，如果超过，就禁止写数据

# 过期删除
redis会对key设置过期时间，Redis会把key带上过期时间存储到一个过期字典

## 惰性删除
就是没访问一个key才检查key过期，不主动删除过期键
只会调用很少的系统资源，但是会造成内存空间浪费
## 定期删除
字典中随机抽出20个带有ttl的key，如果其中超过25%都过期了，再执行一次

### 主从模式
RDB和AOF都分为两个阶段
RDB：
- 文件生成：会检查过期
- RDB加载：看主还是从
AOF：
- 写入：不检查，如果过期删除了，redis会给AOF加一条的
- 重写：检查

# 内存淘汰
LRU vs LFU 
redis这里实现的有区别，因为双向链表遍历的开销太大，所以他就是在key旁边再附上最近一次访问的时间，随机取5个，淘汰掉最小的

# 缓存设计
## 缓存雪崩
大量缓存数据在同一时间过期失效，且此时有大量用户请求，都无法在Redis里处理，于是全部请求都直接访问数据库，从而导致数据库的压力骤增

- 可以在原有失效时间上加上一个随机的时间，这样过期时间就不重复了，降低了缓存集体同时失效的概率
- 互斥锁
## 缓存击穿
一个热点数据过期，此时大量请求要访问该热点数据，就无法从缓存读取，要去数据库，被高并发的请求冲垮

- 可以使用互斥锁
### 互斥锁的问题
- 阻塞
- 如果在加锁之后请求进程崩了，锁不释放，GG
- 惊群效应
拿锁失败，客户端自己决定等不等，等多久
## 缓存穿透
用户访问的数据既不在redis也不再数据库中，用户先查缓存发现缓存缺失，再去访问数据库时，数据库中也没有要访问的数据。遇到大量这样的请求，数据库的压力也很大

这种一般是业务误操作或者黑客恶意攻击

- 非法请求限制
- 使用布隆过滤器快速判断数据是否存在

# 缓存一致性
当我们进行写操作时，在缓存旁路模式里，面对写请求时，我们的标准动作是先淘汰(删除)缓存
## 先删redis还是先写MySQL
- Redis：线程A更新，先删了Redis。线程B进来，cache miss，查数据库，查到旧数据，塞回redis了，随后线程A把新数据写进MySQL

MySQL是新值，redis里永远是旧值

- MySQL：**推荐做法**哪怕线程B在线程A写MySQL的瞬间来读了，也只是读到redis的旧值。随后A写完MySQL他会删缓存的，之后再读到这个数据的时候，写回缓存了，数据ok✅️

### 延迟双删
最终解决方案
先删一次redis
写MySQL
写完继续删redis

## 兜底机制
即使先写了MySQL，但是删redis的时候，崩溃，删缓存这一步失效，和先删redis发生了一样的问题了

这时候我们看到 `binlog`

- 业务代码只管一件事，把数据更新到MySQL，成功写完就返回给用户，不用操心redis
- 监听日志：引入一个中间件，伪装为MySQL的从库，一旦MySQL有了更新操作，监听到binlog日志
- 中间件把这个更新时间丢给消息队列，又消费者去负责删除对应的redis缓存
- 如果这时候redis宕机或者因为网络抖动导致删除失败，消息队列的特性就是不成功就一直重试

将写数据库和删缓存解耦了
