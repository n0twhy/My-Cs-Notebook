## http 3.0
### QUIC
- 多路复用，一条连接上可以并发传输多个stream，stream就可以看成是一条http请求
由于QUIC协议使用的是UDP，UDP不关心包的顺序，也不管丢失与否
QUIC会保证包的可靠性，每个stream有各自单独的序号当某个stream中的一个数据包丢失，即使其他数据包到达，数据也不会被http3读取，直到QUIC重传报文

- 连接迁移：由于tcp是四元组，切换wifi的时候ip会变，需要重新建立连接，然后慢启动。但是QUIC使用连接id来标识通信的两个端点，即使IP变化，只要上下文没变，就可以无缝复用原连接
### 为什么很多公司主力还在HTTP2？
- 运营商对UDP不友好，为了防止DDOS攻击，会被限速和丢包
- QUIC占CPU，因为每个数据流都需要解密

# TCP & UDP
## TCP 三次握手
client                                  server
  │                                       │  LISTEN
  │────── SYN (seq=x) ──────────────────→│  (进半连接队列)
  │ SYN_SENT                             │  SYN_RCVD ← 这个状态你漏了
  │                                       │
  │←───── SYN+ACK (seq=y, ack=x+1) ──────│
  │                                       │
  │────── ACK (ack=y+1) ────────────────→│  ESTABLISHED
  │ ESTABLISHED                          │  (从半连接队列→全连接队列)

client -> SYN_SENT -> ESTABLISHED
server -> SYN_RCVD -> ESTABLISHED
### 为什么是三次不是二次四次
- 防止旧的重复连接初始化造成混乱
- 还有就是保证双方都有接受和发送的能力，我们考虑一个场景，比如我和面试官您一开头的时候，是不是您先说了一句“喂”，然后我说了一句“喂，听得到吗”，最后您说“听得到”。这个就是我和您之间的三次握手，您先说喂，想知道自己的语音能不能送到我这，我能不能听到你讲话，我说喂也是要确认您能不能准确听到我讲话，您说听得到，我就知道了。我们这个通话可以建立。如果只有两次，最后我没有听到您说听到了，我就不能确定我这边麦克风是否有正确接收我的声音送过去让您听到，不是四次的话，就是三次已经足够保证这个通话可以建立了
### 如果第三次ACK丢失
server 侧：还在 SYN_RCVD 状态，超时重传 SYN+ACK（Linux 默认 5 次、指数退避），重传完都收不到 ACK 才放弃、从半连接队列移除。

### accept
完成三次握手后，进入内核的全连接队列，调用accept就是把连接取出来给用户使用

### 大量SYN包怎么办
- 增大内核tcp的半连接队列
- 减少SYN+ACK重传次数

## 四次挥手
client (主动关)                           server (被动关)
  │ ESTABLISHED                              │ ESTABLISHED
  │                                          │
  │──── FIN ────────────────────────────→   │
  │ FIN_WAIT_1                               │
  │                                          │ ← 收到 FIN
  │←─── ACK ──────────────────────────────   │ CLOSE_WAIT ← 是 server 进这个状态！
  │ FIN_WAIT_2                               │
  │                                          │ (server 把剩余数据发完)
  │                                          │
  │←─── FIN ──────────────────────────────   │
  │                                          │ LAST_ACK
  │──── ACK ────────────────────────────→   │
  │ TIME_WAIT                                │ CLOSED
  │ (等 2 MSL)                               │
  │ CLOSED                                   │

  FIN_WAIT_1 -> FIN_WAIT_2 -> TIME_WAIT -> CLOSED
  CLOSE_WAIT -> LAST_ACK -> CLOSED
### TIME_WAIT 为什么是 2MSL
保证最后一个 ACK 能到对方（丢了对方会重传 FIN，自己还能再回 ACK）
让本次连接的所有旧包在网络里消亡，避免影响下一次连接
### 四次挥手为什么不能合并
server 收到 FIN 后可能还有数据要发完，所以不能立刻回 FIN，先回ACK让对方知道自己已经收到对方的关闭请求。自己的数据发完再回FIN
### MSL -- maximum segment lifetime

### 出现大量TIME_WAIT
- http没有使用长连接
- 端口复用

### CLOSE_WAIT大量堆积
server 收到对方 FIN， 回了ACK，进入CLOSE_WAIT，等待本地应用调用close然后发送FIN。
百分之九十九的原因是应用层代码bug，没有调close()

### SYN FLOOD
攻击者伪造源IP大量发送SYN，server回送ACK+SYN进入SYN_RCVD,但是源IP伪造的，收不到第三次ACK，SYN就在半连接队列里占着，把真用户挤出去了
- 增加半连接队列，减少超时重传次数
- 收到SYN后不分配资源，而是发一个带cookie的SYN+ACK，真用户会通过cookie解码返回cookie+1，假的用户不会回ACK
## TCP和UDP的区别
### 连接
- TCP：面向连接，点对点
- UDP：不需要握手连接，直接传输，可一对多，多对一，多对多
### 可靠性
- TCP：可靠性强，可以无差错不重复按序到达
- UDP：不可靠
### 拥塞控制，流量控制
- TCP有，UDP都没有
### 头部开销
- TCP大，一般在20个字节。UDP固定8个字节
UDP:[源端口 2B][目的端口 2B][长度 2B][校验和 2B]

## TCP为什么可靠
- 连接管理：三次挥手，四次握手
- 序列号：保证数据一致性，避免数据重复，保证数据有序
- 流量控制、拥塞控制

## TCP粘包
小包攒起来合并发，为了节省TCP头的开销，把多此send合成一个TCP段

解决：固定长度的消息，定义特殊字符作为边界

## 滑动窗口
wnd = min(rwnd, cwnd)
rwnd是对方告诉你他能收多少(流量控制)
cwnd是自己估的网络能承受多少(拥塞控制)

## TCP的流量控制
- 1.已发送并收到ack确认的数据
- 2.已发送但没有收到ack
- 3.可用窗口，未发送的且在接收方处理范围内的
- 4.超过接收方处理范围

## TCP的拥塞控制
- 慢启动：每得到一个ack，拥塞窗口的大小+1.(指数级增长)
- 拥塞避免：到达一定量时，变成线性增长
- 拥塞发生：网络出现拥塞，有两种重传机制：
超时重传：发了一个包，启动定时器，如果规定时间内没有收到ack，那么重传一次
快速重传：超时重传太慢，如果短时间内重复收到三个相同的ack，直接重传对应的ack包
- 快速恢复，重传后不回到慢启动，直接到拥塞避免状态，避免抖动
### SACK
将已收到的数据传给对方，告诉对方中间哪些数据没收到

## TCP keepalive
这个是内核态，和HTTP的完全不同
如果两端超过一段时间没有任何的数据交互，就会触发tcp保活机制，内核发送探测报文
### 主机崩溃
如果服务端没有开启keepalive，那么一直就是established状态
### 进程崩溃
会有四次挥手
