## b+树索引
现代MySQL，主要分为聚簇索引和二级索引
聚簇索引：b+树的叶子就是一整张表
二级索引：b+树叶子value是主键，用key拿到主键就会回表再查一次

### 为什么二级索引存的是主键
如果存物理RID的话，如果页分裂或者迁移，那么所有二级索引的RID都要更新

### 如果没有主键怎么办
- 找第一个非空唯一索引
- 自己造一个隐藏列当索引

### 为什么自增最好
总在叶子最右边，能减少中间的页分裂，逻辑相对没那么复杂
### 为什么用b+树？
IO友好，查找删除插入logn
- 对比红黑树，他的IO小
- 对比B树，他还是更矮胖，他的internal node不存数据，只存key和叶子的RID
叶子有序单链表，天生适合遍历排序，

### 联合索引
几个key一起，然后按照字典序排序
#### 最左前缀匹配原则
必须从最左列开始，连续往右边用

另外，普通where不同，普通where与顺序无关，优化器会自动重排

# 事务 MVCC
## 特性
- A(atomic)原子性，全部操作要么完成，要么不完成，不应该有中间态
- C(consistency)一致性，
- I(isolation) 隔离性  允许多个并发事务进行读写和修改
- D(durability)持久性  事务处理结束后，对数据的修改应该是永久的

## 问题
- 脏读：读到了另一个还没提交的数据
- 不可重复读
- 幻读
| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
| --- | --- | --- | --- |
| RU（读未提交） | 会 | 会 | 会 |
| RC（读已提交） | 不会 | 会 | 会 |
| RR（可重复读） | 不会 | 不会 | 会* |
| Serializable（串行化） | 不会 | 不会 | 不会 |
### 2PL解决方案
加锁，分为growing和shrinking
growing：可以获取任何锁，但不能解锁，解锁立马进入shrinking
shrinking：只能解锁，不能获取任何锁
why：A = 100, B == 100, T1负责A给B转账50，T2负责读总和
T1写完A-50 = 50释放锁， 这时候B = 100，结果T2趁虚而入，读到A+B=150??????这不可能！
T1回来，继续B+50 = 150
that's why
- RU完全不加读锁
- RC读完立马解锁
- RR事务提交才解锁
- serializable就是在RR基础上，Next-Key Lock防止幻读
### MVCC解决方案
- RU 直接读最新的版本
- RC 每个select生成ReadView，同一事务会看到
- RR 事务第一次select生成一个Read View，直接用到事务结束(注意高并发状态，undolog可能你得遍历几千行才能找到对你可见的版本，而RC几乎每次都是新的，不用怎么遍历)
- 串行化：退化2PL

## MVCC
- 每个tuple的背后  都有两个隐藏的trx_id和undolog_ptr
```
当前 row（最新版本）
├─ DB_TRX_ID = 100  ← 事务 100 改的
├─ DB_ROLL_PTR ──┐
└─ data: name='Bob', age=30
                 │
                 ▼
         undo log record（旧版本）
         ├─ DB_TRX_ID = 80   ← 事务 80 改的
         ├─ DB_ROLL_PTR ──┐
         └─ data: name='Bob', age=25
                          │
                          ▼
                  undo log record（更旧版本）
                  ├─ DB_TRX_ID = 50
                  ├─ DB_ROLL_PTR = NULL（链尾）
                  └─ data: name='Alice', age=20
```
- 同时会生成一个Read View快照，里面包含creator_id, min_id, max_id, m_ids

以undolog里的版本号作为T
1. T == RV.creator_id        → ✅ 可见（我自己改的）
2. T < RV.min_id              → ✅ 可见（早就提交了）
3. T >= RV.max_id             → ❌ 不可见（在我快照之后才出现）
4. RV.min_id <= T < RV.max_id：
   ├─ T ∈ RV.m_ids           → ❌ 不可见（快照时还活跃）
   └─ T ∉ RV.m_ids           → ✅ 可见（快照时已提交）

# 日志
## undo log
原子性的代表，也用于回滚
每当对一条记录进行写的时候，都要记录在undolog里

## redo log
持久性的代表
用途：崩溃恢复
物理日志，写入方式是WAL(write ahead logging)修改数据页前，先写redolog

### why need redolog
innoDB的写操作不是直接写磁盘，而是写bufferpool里，然后脏页由后台线程慢慢刷盘
### WAL Write Ahead Logging
写操作并不是立刻写到disk里边，而是先写日志，然后在合适的时间写会磁盘
### 刷盘
redolog的两层缓冲：
redo log buffer(内存) -> Os cache buffer(内核缓冲) -> 磁盘(真正持久化)
flush log:
- 每秒刷一次，无视提交
- 每次提交都刷
- 提交时只做写到Os cache，每秒Os cache到磁盘

## bin log 
和redo有点像，但是这个用于主从复制和备份恢复，是全量逻辑日志，保存了所有日志变更的情况，如果写满一页就再开一页继续写，redo是写满一页保存，再从同一页开始写

### why need binlog
主从复制需要他，从库拉去主库的binlog，在自己这边重放，达成数据同步。备份恢复也靠他

## 物理日志 逻辑日志
物理日志，底层改：内存，磁盘
逻辑日志，操作逻辑：比如记录的是原始的SQL语句
## 2PC，两阶段提交
```
写redolog成功了，但是binlog崩了，会发生什么？
主库有redolog恢复这个update，但是从库是从binlog拉取数据，意味着从库再也拿不到这个数据了，**主从不一致**
```

redolog的写入拆成 prepare和commit两步，中间夹一次binlog的写入

事务提交时:
  ① InnoDB 写 redo log,标记为 PREPARE 状态  → 刷盘
  ② Server 层写 binlog                       → 刷盘
  ③ InnoDB 把 redo log 标记改成 COMMIT       → (这一步可以不立刻刷盘)

重启时，扫描redolog，根据每条事务的状态决定如何处理
- state1：redolog处于commit，直接redo就好，
- state2：redolog处于prepare，但是binlog存在，视为已经提交
- state3：redolog处于prepare，但是binlog不完整。说明1成功，2还没完成就崩了，从库没收到，不确认数据一致性，视为未提交，回滚。

## UPDATE user SET age = 20 WHERE id = 1 中间发生了什么？
- 定位数据页，B+ -> Bufferpool，不在就去磁盘加载
- 写 undolog
- 修改 bufferpool 里的页
- 写 redolog buffer(物理日志)
- 写 redolog,标记prepare，刷盘
- 写 binlog (逻辑日志),刷盘
- redolog标记commit
- 返回客户端“OK”

# 死锁
- 我的bustub lockmanager死锁检测周期是50ms，这是个经验值，用户几乎感知不到，CPU开销可以接受

- InnoDB的真实做法：
每次加锁失败都跑一次，
根据undolog的量来选择该杀那个事务，然后回滚。
如果深度过深(>200)，或超高并发的热点更新场景，关闭检测，直接放弃搜索，视为死锁，交由超时机制来处理

```
Master                         Slave

  ┌──────────────┐              ┌──────────────┐
  │              │              │              │
  │   Write Op   │              │              │
```

## 为什么需要relay log
- 速度不匹配  网络不稳定
IO线程从网络收数据，很快
SQL线程：在从库执行一遍，包括加锁改bufferpool，写redolog，要慢得多

加上relaylog作为中转站，这两步就解耦了
崩溃不会丢数据，磁盘文件不怕大
IO线程和SQL线程异步工作

## 主从延迟
用户写操作要隔几秒才看到自己修改的数据：
读写分离：主库写，从库读，主从复制有点慢，用户前两秒读到的还是从库的旧数据

- 强制写后读走主库， 用户写操作的N秒内，所有读请求强制路由到主库
- 主库提交事务后，等到从库写完relaylog回ACK才返回成功
